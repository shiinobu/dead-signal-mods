# ENTITY RESOLUTION — Character & Email Contract

## Status

**ACTIVE CONTRACT — 2026-09-12**

## Purpose

Character email addresses are canonical story identity. They must not be randomly generated at runtime.

## Rules

1. Every recurring character has one stable character ID, display name, and email address.
2. Character email addresses are defined in the content layer, not generated by `Random` APIs.
3. Fictional ENTITY RESOLUTION addresses use the `.lock` domain.
4. Organization mailboxes may use organization-specific `.lock` domains such as `@skynet-logistics.lock` or `@arka-systems.lock` when the story requires them.
5. Quest-critical mail must reference a canonical character email rather than an inline random address.
6. Quest-critical subjects and report bodies are canonical content constants so live validation is deterministic.
7. The player should not be required to invent or guess quest-critical recipient, subject, or report text.
8. Until a supported native draft/prefill API is verified in the HackHub runtime, the implementation must not invent a keyboard or mail-composer API. The current interim contract exposes the exact recipient, subject, and plain-text report template in the quest briefing and validates the sent message against the canonical contract.

Do not create per-quest random email aliases for recurring story characters.
